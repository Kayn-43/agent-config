# Embodied AI workflow

具身方向的成本结构和纯软件不同：**硬件时间、仿真时间和真机时间是三种不同的稀缺资源**。工作方式要围绕这一点组织。

## 在真机上做任何事之前

1. 确认机器人的急停手段可用，且有人能触达。
2. 确认电池/供电状态。
3. 确认工作区没有无关的人在设备活动范围内。
4. 先做**最小风险验证**：小幅动作、低速、短时长。

真机调试的顺序永远是：仿真 → 低速小动作 → 逐步放开。不要跳过。

## 环境隔离

具身项目对环境极其敏感，混用会得到无法解释的行为：

- ROS1 与 ROS2 **不能共用**一个 shell 环境
- 仿真 Python、ROS 的 Python、训练用的 conda 环境是**三套**
- 不同机器人/不同项目各自独立的环境；不要把一个项目装好的依赖当成另一个也能用

启动前先读项目的 README 与启动脚本，不要凭猜测。

## 工作区分层

典型的工作区划分（按项目实际结构调整）：

| 层 | 职责 |
|---|---|
| 仿真环境 | 场景、传感器、物理参数 |
| 策略/算法 | 训练、推理、检查点 |
| 桥接层 | 仿真 ↔ ROS ↔ 真机的消息转换 |
| 真机驱动 | 硬件接口、安全限幅 |

**先在仿真里定位问题，再往下层推进。** 在真机上排查算法问题，成本高且噪音大。

## sim-to-real 的现实

仿真里能跑不等于真机能跑。常见落差来源，按出现频率：

1. **观测分布差异** —— 传感器噪声、延迟、缺失；仿真是理想化的
2. **动力学差异** —— 摩擦、质量分布、执行器响应、地面刚度
3. **时序差异** —— 控制频率、通信延迟在仿真里常被忽略
4. **状态初始化** —— 真机永远不在完美的初始状态
5. **域随机化不足** —— 只随机化了训练用的那几项

评估 sim-to-real 时，**单独报告仿真指标和真机指标**，不要混在一张表里。

## 训练与实验

- 固定随机种子并记录；具身训练方差通常很大
- 报告多次运行的分布，而不是单次最好结果
- 记录环境版本、物理参数、随机化范围——否则结果无法复现
- 长训练前先跑短程验证：确认损失在动、检查点在存、日志在写

## ROS 侧常见幽灵问题

| 现象 | 常见原因 |
|---|---|
| 两边都正常但互相看不到话题 | `ROS_DOMAIN_ID` / `RMW_IMPLEMENTATION` 不一致 |
| 话题存在但收不到数据 | QoS 配置不匹配 |
| 频率远低于预期 | 回调阻塞、单线程执行器、日志刷屏 |
| 时间戳异常 | 仿真时间与系统时间混用（use_sim_time） |

遇到这类问题，先核对**环境变量与 QoS**，再怀疑代码逻辑。

## 汇报格式

```
平台        : <机器人 / 仿真环境>
环境        : <ROS 版本, Python 环境, 仿真器>
层级        : <仿真 / 桥接 / 真机>
Command     : <实际执行>
Result      : <观测到的行为，而非"已完成">
Metrics     : <仿真与真机分开列>
Safety      : <急停是否就绪 / 是否有速度或力限幅>
Unverified  : <未验证的部分>
```

**任何真机测试都必须显式说明安全前提是否满足。** 这是这一条里唯一不能商量的事。
