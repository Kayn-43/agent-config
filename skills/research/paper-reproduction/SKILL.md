# Paper reproduction

复现的目标是**回答"能不能得到报告的结果"**，不是"跑起来一个像样的东西"。

## 顺序不能颠倒

```
读论文 → 找官方实现 → 固定环境 → 跑通最小配置 → 复现单个数字 → 复现主表 → 消融
   ↑                                              ↑
   └────────── 任何一步没通过，不要跳到下一步 ──────┘
```

最常见的浪费是：环境还没跑通最小配置，就去跑主实验，然后拿到无法解释的数字。

## 1. 先明确要复现什么

从论文里提取**具体的、可对照的数字**：哪个表、哪一行、什么指标、什么设置。

不要以"复现这篇论文"为目标——那是无法判定完成的任务。

```
目标指标      : <表 X 第 Y 行>
论文报告值    : <数值 ± 方差（如果论文给了）>
可接受偏差    : <自己定一个阈值，事先定好>
```

**事先定好容差**，否则事后很容易把任何结果都解释成"基本一致"。

## 2. 找官方实现，优先于自己重写

顺序：

1. 作者官方仓库（看论文里给的链接，注意有没有更新版）
2. 作者提供的检查点/权重
3. 社区高质量复现（作为交叉验证）

**记录你用的是哪个 commit。** 主分支会变，今天的复现结果明天就解释不了。

## 3. 环境固定

复现失败的原因里，环境占很大比例。

- 用项目提供的环境定义文件优先（`environment.yml`、`requirements.txt`、Dockerfile）
- **记录精确版本**，包括 CUDA、驱动、Python、关键库
- 不要用 `latest` 或不锁定的依赖
- 装依赖前看 `df -h`——数据集和权重通常很大

## 4. 最小配置先跑通

用一个最小的设置（小数据子集、少步数、单 GPU）确认整条链路能走通：数据加载 → 前向 → 损失 → 反向 → 保存 → 评估。

这一步能拦住绝大多数"跑了几小时才发现有问题"。

## 5. 对不上时的排查顺序

按信息量从高到低：

1. **数据**：划分方式、预处理、增强、样本数是否与论文一致
2. **超参**：学习率、batch size、warmup、训练步数（论文常写不全，去查代码默认值）
3. **评估口径**：指标定义、是否用 EMA 权重、测试时增强、取最佳还是最后一次
4. **随机性**：种子、是否多次运行取均值
5. **硬件相关**：混合精度、不同 GPU 上的数值差异
6. **代码版本**：是不是用错了分支或旧 commit

**先怀疑口径差异，再怀疑实现有 bug。** 前者远比后者常见。

## 6. 如实报告

复现结果与论文不一致时：

- 论文错了、代码与论文不符，都是**合法结论**，不要为了"复现成功"去调参凑数
- 报告你实际改了什么才得到结果——这本身就是有价值的信息
- 明确区分：原样跑 vs 改动后跑

**不要做的是**：反复调参直到数字接近论文，然后声称复现成功。那是拟合，不是复现。

## 输出格式

```
论文 / 目标       : <出处, 目标表与行>
官方实现          : <仓库 + commit>
环境              : <CUDA / Python / 关键库精确版本>
设置              : <数据规模, 步数, 硬件>
论文报告值        : <数值>
复现值            : <数值>  (运行次数: N)
偏差              : <差值, 是否在事先设定的容差内>
与原样的偏离      : <改了哪些东西, 为什么>
结论              : 复现成功 / 部分复现 / 未能复现 / 环境阻塞
阻塞点            : <卡在哪一步, 具体报错>
未验证            : <没做到的部分>
```

最后一栏必须诚实。**"未能复现"加上清楚的阻塞点是可用的结论；模糊的"基本一致"不是。**
