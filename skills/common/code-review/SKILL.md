# Code review

目标是**找出问题**，不是确认代码没问题。

## 顺序

先读改动意图（提交信息、PR 描述、任务背景），再读 diff。没有意图就无法判断"这是 bug 还是有意为之"。

```bash
git status --short
git diff                    # 未暂存
git diff --staged           # 已暂存
git diff <base>...HEAD      # 相对基线
```

## 检查清单

**正确性**
- 边界条件：空集合、单元素、越界、零、负数
- off-by-one
- 空值 / 未初始化 / 未定义与空字符串的区别
- 错误路径是否真的被处理，而不只是被 catch 后吞掉

**回归**
- 改动是否影响其他调用方
- 默认值变化是否改变了既有行为
- 是否删掉了别人依赖的东西

**接口一致性**
- 参数顺序、命名、返回类型是否与同类接口一致
- 调用方与实现是否同步更新

**并发与状态**
- 共享状态、竞态、可重入
- 资源释放（文件句柄、连接、锁）

**安全**
- 命令注入、路径穿越、未校验的外部输入
- 密钥、令牌、凭据是否被写进代码或日志
- 破坏性操作是否有防护（参见 `server-safety` 的思路）

**范围**
- 是否夹带了与任务无关的改动
- 是否顺手重构了不该动的地方

## 常见"假成功"模式（高优先级）

这些比语法错误更危险，因为它们会静默通过：

- 退出码为 0 但实际什么都没做（Windows 上的 python 商店桩、0 字节占位可执行文件）
- 命令被引号/转义问题截断，却返回成功
- 测试存在但断言没被执行到
- 异常被捕获后只打日志、返回默认值
- 验证步骤依赖的是缓存结果而非本次实际输出

## 输出格式

每条发现给出：严重度、文件与行号、问题、为什么是问题、建议修法。

```
[P0] file.py:42 — <一句话结论>
  问题: <具体描述>
  原因: <为什么会出问题>
  建议: <怎么改>
```

严重度约定：

- **P0** 正确性错误、数据损坏、安全隐患
- **P1** 明确的回归风险或逻辑缺陷
- **P2** 可维护性、一致性
- **P3** 风格

## 规则

- 只报**可执行**的问题。不要报"可以更好"这种无法落地的意见。
- 不确定的标注为"需要确认"，不要伪装成确定结论。
- 不要因为没有发现 P0 就宣称"没问题"——说清楚**检查了什么、没检查什么**。
- 不做与本次改动无关的评审。
